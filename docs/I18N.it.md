# Internazionalizzazione

[English](I18N.md) | **Italiano**

## Cataloghi e fallback

`alterecho/locales/en.json` è il catalogo di riferimento; `it.json` contiene la traduzione italiana completa. Python e Svelte usano gli stessi JSON: i codici degli errori hanno una sola definizione. Le chiavi descrivono messaggi di presentazione e rimangono stabili quando cambia il testo. I valori sono stringhe o oggetti con forme plurali. `_meta` contiene nome nativo della lingua e metadati Python per numeri, date e plurali.

Python usa `importlib.resources`, una lingua locale al contesto e la libreria standard. Vite include tutti i cataloghi tramite glob eager. Non servono servizi di traduzione o Internet durante l'esecuzione. Una chiave tradotta mancante usa l'inglese; una chiave assente anche dal riferimento produce un messaggio generico leggibile e diagnostica debug, senza bloccare il client. I test rifiutano duplicati, chiavi discordanti e parametri incompatibili.

```json
{
  "_meta": {
    "name": "Italiano",
    "plural": "n != 1",
    "pluralCategories": ["one", "other"],
    "decimal": ",",
    "group": ".",
    "dateFormat": "%d/%m/%Y %H:%M"
  },
  "web.delete_topic": "Eliminare “{topic}”?",
  "web.messages": {"one": "{count} messaggio", "other": "{count} messaggi"}
}
```

I parametri sono testo semplice, mai HTML o espressioni eseguibili. Le parentesi degli esempi JSON restano intatte. Svelte esegue l'escape delle traduzioni; soltanto il renderer Markdown sanitizzato delle conversazioni gestisce HTML. Il frontend usa `Intl` per numeri, date/orari e plurali. Python usa separatori/formato del catalogo e il compilatore di espressioni plurali gettext della libreria standard. Ulteriori forme si dichiarano con `pluralCategories` ed espressione gettext, senza condizioni nel codice per ogni lingua.

## Comportamento del browser

Automatico sceglie la prima lingua supportata nell'ordine di `navigator.languages`, normalizzando varianti come `it-CH` ed `en-GB`; senza corrispondenze usa l'inglese. La selezione manuale prevale sul browser ed è salvata in local storage come `alterecho-language`. Automatico riattiva il rilevamento. Se lo storage è bloccato, la lingua funziona nella sessione corrente senza persistenza. Si aggiorna anche `lang` del documento.

Il selettore è disponibile prima del login, nella sidebar, nelle impostazioni e nelle modali. Gli store Svelte aggiornano testi, modali aperte, errori e notifiche senza ricaricare, navigare, interrompere SSE, ricreare la chat, azzerare moduli o scorrimento. La preferenza appartiene al profilo/origine del browser, non al server. Altri browser/profili mantengono la propria scelta; le schede che condividono lo storage non ricevono un cambio forzato durante una sessione attiva.

## Rilevamento e precedenza CLI

1. Opzione globale esplicita `--lang`.
2. `ALTERECHO_LANG`, se impostata.
3. Preferenza in `client-language.json`, accanto a `client.json`.
4. Locale del sistema.
5. Fallback inglese.

`auto` al livello selezionato richiede il rilevamento del sistema, senza consultare preferenze esplicite inferiori. Gli override da comando/ambiente non vengono salvati. **Impostazioni → Language / Lingua** modifica soltanto la preferenza persistente; eventuali override espliciti/ambiente rimangono prioritari.

Negli ambienti headless si controllano `LC_ALL`, poi la lista ordinata `LANGUAGE`, `LC_MESSAGES` e `LANG`. Senza variabili utilizzabili, Windows usa `GetUserDefaultLocaleName`; Linux/macOS usano le informazioni locale di Python. Si normalizzano `_`/`-`, suffissi encoding/modificatore e varianti regionali. Locale assente o non supportato usa l'inglese; `C`/`POSIX` usa il fallback quando non esistono preferenze supportate.

```sh
alterecho --lang en help
alterecho --lang it help
alterecho --lang auto status
```

Per l'ambiente: `export ALTERECHO_LANG=it` oppure `$env:ALTERECHO_LANG='it'`. Comandi, flag, endpoint, enumerazioni e chiavi di configurazione non vengono rinominati. La lingua della CLI non determina quella della generazione.

## Errori server e compatibilità

La diagnostica del server usa l'inglese. Gli errori applicativi conservano `detail` e aggiungono `code`/`params` quando disponibili. La validazione conserva la lista precedente di `loc`/`msg`/`type` e aggiunge un codice generico traducibile. Snapshot, diagnostica provider ed eventi di errore possono aggiungere `error_info`, conservando i campi esistenti. Credenziali note vengono rimosse da dettagli e parametri.

I client traducono i codici riconosciuti nella propria lingua. Errori legacy/sconosciuti e diagnostica esterna restano leggibili come ricevuti. Non esiste una lingua globale del server né una modifica dello stato condiviso guidata da `Accept-Language`.

Argomenti, prompt, ruoli, personalità, posizioni, risposte, JSON canonici, checkpoint e sessioni Codex sono dati: non vengono tradotti. I prompt/default italiani esistenti restano per compatibilità. Gli export offline conservano contenuti e involucro preesistente; cambiare lingua non li riscrive né migra gli storici.

## Aggiungere una lingua

1. Copia `en.json` in un catalogo come `fr.json` o `zh-CN.json`, impostando il nome nativo in `_meta.name`.
2. Traduci i valori conservando chiavi e parametri. Imposta separatori, date, espressione/categorie gettext Python e le forme plurali `Intl` necessarie.
3. Mantieni invariati comandi, ID modello/provider, endpoint ed esempi tecnici; non tradurre dati utente interpolati.
4. Esegui test dei cataloghi Python, test/check frontend e ricompila frontend/pacchetto. Registro e selettori scoprono i JSON disponibili senza modifiche al codice applicativo.
5. Verifica contesto, accessibilità e layout con un parlante della lingua. Non aggiungere cataloghi vuoti che fingano supporto.

Non distribuire strumenti temporanei di traduzione, chiamate a traduttori online o credenziali. Commenti/docstring nuovi sono in inglese. Mantieni equivalenti documentazione [inglese](../README.md)/[italiana](../README.it.md), conservando gli originali storici nei propri percorsi.

## Packaging e test

Package data setuptools e `MANIFEST.in` includono `locales/*.json`; la raccolta dati PyInstaller li incorpora. Docker copia i cataloghi nello stage frontend e nel pacchetto Python.

```sh
python -m unittest tests.test_i18n -v
python -m unittest discover -q
cd web
npm run check
npm test
npm run build
npm run test:e2e
```

Le prove operative usano soltanto mock/demo, senza inferenze reali. [Risultati e verifiche rimaste](VERIFICA-I18N.md).
